The assessment

The existing application has useful shared data, permissions and operational building blocks. Its largest remaining weakness is incomplete work between modules: staff can enter a record without being able to complete all the actions, exceptions and follow-up that record requires.

This is a code audit and documented-workflow comparison, not a hands-on certification of the external products. The comparison is representative, not exhaustive. The requirements below are recommendations tailored to AH Interiors, not claims that every vendor implements every item identically.

Scope of this stage: findings and an implementation specification. No application behaviour was changed during this review. Earlier browser checks covered selected paths; they did not establish complete business readiness. A future-proof guarantee would be misleading: the practical protection is explicit acceptance scenarios, configurable rules and a realistic staff pilot.

P0 = correct before trusting the affected operational data or restricted access. P1 = complete before relying on that module for everyday work.

Defects and gaps to address first

These findings come from the present repository. They identify concrete failure paths and missing actions; no destructive live-data reproduction was performed.

F01P0

Delivery completion is not scoped to its fulfilment group

A delivery for one group can consume another group's reserved stock. This is a code-path finding, not a claim that live stock has already been affected.

Code evidence and acceptance check

Evidence: server/services/operational.ts, Delivered transition: selects all active reservations for orderId and consumes them in a loop; the earlier Ready to Book check does filter groupId.

Check: Create a two-group order. Deliver group A. Group B's stock, reservation and order progress must remain unchanged.

F02P0

Purchase total can include superseded draft lines

Editing a draft can leave a displayed total that disagrees with its visible lines.

Code evidence and acceptance check

Evidence: server/services/purchasing.ts, listPurchases: items returned to the UI filter active rows, but totalPence sums all historical rows for the purchase order.

Check: Edit the same draft twice. Its list, detail and printed total must equal only the current active lines.

F03P0

Reported contribution does not use actual complete costs

A customer delivery charge is not necessarily the delivery expense. The reported contribution can therefore misstate profitability.

Code evidence and acceptance check

Evidence: server/services/reporting.ts, orderMargin: starts from emptyCosts and treats order total minus product revenue as delivery cost. Recorded delivery, assembly and other fees are not reconciled into that calculation.

Check: Use an order with independently recorded delivery revenue, actual delivery expense, assembly and fees. All margin screens must agree with the same cost breakdown.

F04P0

Catalogue role controls need field-level consistency

The history route can expose costs hidden elsewhere, and editing is inconsistent for restricted staff. This needs endpoint and UI fixes together.

Code evidence and acceptance check

Evidence: server/services/catalogue.ts: productHistory permits catalogue.write, including Shopify Store Manager, while listProducts redacts costs for that role. The same role can access the full-product save endpoint. Redacted records also omit fields/version used by the editor.

Check: Test each role's list, history, editor and direct API writes. Restricted fields must stay private and protected while permitted edits remain possible.

F05P1

Service cases cannot select their sales order in the current form

The case can name a customer, product and supplier without the staff member being able to connect the affected purchase.

Code evidence and acceptance check

Evidence: lib/business-modules.ts sets customer:true but no order flag for service-cases; components/operational-workspace.tsx renders order selection only when definition.order is enabled.

Check: Create a case from an order and from the case page. The customer, order and affected order lines remain linked.

F06P1

Some task relationship options cannot be saved

The UI offers a relationship that the server rejects.

Code evidence and acceptance check

Evidence: The task form offers purchase-order and supplier-order; server/services/operational.ts linkedRecord does not resolve either entity type.

Check: Every selectable relationship must resolve, save and open its linked record. Replace raw ID entry with a record picker.

F07P1

Search and notifications stop short of the target record

A user has to search again after opening a relevant result or notification.

Code evidence and acceptance check

Evidence: server/services/reporting.ts builds module-level hrefs for operational results; NotificationCenter renders the message and Mark read but no record link.

Check: Open a result or alert, refresh the URL, and land on the exact permitted record with the relevant action visible.

F08P1

Settings and reporting definitions are inconsistent

A configured channel may be unavailable and the same work may be counted differently on different pages.

Code evidence and acceptance check

Evidence: server/validation.ts uses fixed legacy channels while business settings exposes configurable channels. Reporting uses UTC boundaries; operational views use browser-local day values. Supplier overdue calculations differ between dashboard and supplierFlags.

Check: Use one configured channel list, one business timezone and shared definitions for every metric and overdue state.

F09P1

Flooring quantities cannot flow through stock and purchasing

A valid flooring estimate cannot be carried accurately through every later stage without an explicit unit and conversion model.

Code evidence and acceptance check

Evidence: lib/flooring.ts calculates fractional square metres; purchaseItems, stockBalances, stockReservations and stockMovements use integer quantities.

Check: Quote 18.6 m², round to a product's box or roll requirement, purchase, receive, allocate and return quantities with no silent rounding.

F10P1

Some visible workspaces still use local sample data

The Documents and Communications pages are not yet the shared operational tools their navigation implies.

Code evidence and acceptance check

Evidence: components/mail-workspace.tsx uses sampleMail/local drafts; app/documents/page.tsx initializes sample rows and retains only uploaded file names. Persistent record attachments exist separately.

Check: Show only real shared records or an explicit disconnected state; uploads must retain bytes, permissions and linked-record metadata.

What each module must let the team do

Preserve working features and the current stack. Each module should expose its own staff workflow using shared controls, record links, audit history and validation.

The shared screen standard

  1. A clear work queue: saved personal/team views, useful default columns, combined filters, sorting, pagination and bulk actions only where safe and authorised. Keep view state when returning from a record.
  2. A complete record: owner, status, important dates, linked customer/order/product, contextual actions, attachments, related work and a persistent activity timeline. Give it a shareable URL that opens the exact record.
  3. Guided actions: show what is missing before booking, sending, completing or approving. Ask for information at the stage it becomes necessary. Use record pickers and autofill instead of asking staff to copy database IDs.
  4. Recovery: preserve entered data on validation or network failure, prevent duplicate submissions, warn on unsaved changes, handle stale edits with a useful comparison and provide retry or safe reversal where the business allows it.
  5. Truthful states: distinguish no records, no search matches, no permission, unavailable data and disconnected services. Show success only after confirmation; hide synthetic sample records from operational screens.
  6. Daily usability: readable density, keyboard operation, visible focus, touch-friendly field actions, accessible labels/errors, reduced-motion support and retained scroll/filter context. Target WCAG 2.2 AA with manual checks as well as automation.
  7. Measured performance: paginated server queries, debounced search, cancellation of stale requests, appropriate caching and a representative team/data-volume test. Do not infer multi-user readiness from an empty-page screenshot.
  8. Consistent business meaning: one timezone, quantity/unit policy, channel list and set of metric definitions. A UI control must map to a supported server action with the same permissions and rules.

Implementation order

1. Correctness and trust

Fix P0 findings, role-specific behaviour, broken record relationships and conflicting definitions. Remove misleading sample content from operational areas.

2. Shared work surfaces

Exact-record routes, related-record tabs, activity timeline, saved views, useful errors, unsaved-change protection and action-specific forms.

3. Complete fulfilment

Customer → order → purchasing → receipt → reservation → delivery → assembly. Include split suppliers, partial quantities, damage, cancellation and reassignment.

4. Complete exceptions

Flooring survey-to-quote-to-order, customer claims and replacements, returns, credit/refund handling, expenses and policy-enforced approvals.

5. Connect channels

Implement store/mail adapters and visible retry/reconciliation screens. Require credentials only to connect and verify real external services. Define data ownership before synchronising stock.

6. Staff pilot and rollout

Use realistic records under every role, validate totals and permissions, test concurrent edits and recovery, then confirm hosting, scheduled jobs, backup/restore and monitoring.

Connection schemas and mock contract tests can be developed alongside fulfilment work. Advanced route optimisation, automated carpet cut optimisation, a customer portal and AI automation are later options; they should not delay reliable core workflows or appear as working capabilities before integration.

Required business journeys for acceptance

  1. In-stock showroom sale through payment, reservation, delivery and invoice.
  2. Two-supplier ecommerce order with a partial receipt and separate deliveries.
  3. Supplier delay with revised ETA, chase ownership and a customer update.
  4. Warehouse receipt with missing and damaged packs, including remaining quantities.
  5. Customer cancellation before receipt, and cancellation after stock allocation.
  6. Failed delivery, reassignment and a rescheduled customer promise.
  7. Assembly with a missing part and a second visit.
  8. Flooring measure, revised quote, approval, deposit, material purchase and installation.
  9. Damaged item → service case → supplier claim → replacement purchase/delivery.
  10. Partial return with inspection, disposition, credit/refund and margin correction.
  11. Two staff editing the same order while a duplicate store event arrives.
  12. Disabled user, restricted costs, failed upload, lost network and a restored backup.

Screens are accepted when staff can complete these journeys and recover from the exceptions with consistent persistent records. Appearance and automated checks are necessary parts of that review, not substitutes for it.
